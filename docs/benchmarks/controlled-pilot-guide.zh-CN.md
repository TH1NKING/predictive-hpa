# 这轮实验做了什么，为什么这样做

这轮工作完善的是项目的实验验证方法。控制器的预测算法和 API 保持原样；
新增的脚本配置、数据校验和报告，帮助我们判断已有控制器在什么条件下有何表现。
具体步骤和可复现接口见[实验协议](controlled-pilot.md)。
数据、曲线和结论见[完整结果报告](capacity-and-controlled-pilot-20260906.md)。

## 1. 先测应用容量，再比较控制器

固定 1、5、10 个副本时，副本数不会随负载变化。逐级增加每秒计划发出的请求数
（RPS），就能观察应用从正常响应到排队、变慢、超时的过程。

这样做的优点是减少同时变化的因素。直接开启自动扩容压测，看到超时后很难分清：
是负载本来就超出了最大副本的承载能力，还是控制器扩容晚了，或者请求没有到达
新增的副本。固定副本校准先回答前两个实验前提：请求确实分散到各 Pod，而且
增加副本确实能改善某个已测试负载下的服务表现。

这里没有寻找一个精确、永久有效的“最大 RPS”。粗粒度探测加边界确认比较节省
时间；如果要做精确容量规划，可以在拐点附近增加负载档位、延长时间并重复测量，
代价是更多实验时间，而且结论仍依赖当时的应用、资源和环境。

## 2. 为什么成功率、延迟和丢弃请求必须一起看

本轮提前固定的诊断标准是：HTTP 200 比例至少 99%，所有已完成请求的 p95 延迟
不超过 500 ms，且没有丢弃迭代。p95 描述请求延迟分布靠近第 95 百分位的位置，
不能代表每个请求都这么快。

本轮一个实际例子：5 副本在 60 RPS 的 90 秒探针中，5,400 个请求全部返回 200，
但 p95 约为 4.1 秒。只看成功率会把它当作好结果；加入延迟标准后，它明确不达标。

还要分清三个数量：

- **计划负载**：希望压测器每秒发多少请求。
- **完成记录**：客户端得到响应或错误的请求，包括超时这种失败记录。
- **成功请求**：完成记录里真正返回 HTTP 200 的部分。

`dropped_iterations` 是本来应该启动、却没有启动的迭代。它不属于一个已发送
请求的 HTTP 失败。只看已完成请求的失败率，可能漏掉没有发出去的负载；因此
报告单列它，并检查压测器的 CPU、内存及并发配置。

只统计成功请求的延迟也会漏掉超时。所以我们同时保留全请求延迟和成功请求延迟，
并以全请求延迟判断诊断标准是否达成。

## 3. 为什么要延长时间、反向复测

90 秒探针适合尽快找到值得细看的区间；180 秒确认给排队和波动更多时间显现。
这轮 10 副本、80 RPS 的短探针 p95 约为 346 ms，长探针却约为 924 ms。
独立按完成时间分箱后，慢请求也不只出现在长探针开头。

这个差异说明短时通过不能自动推出长期稳定达标。它还不能单独证明差异由时长
引起，因为顺序、此前过载、Pod 历史和主机竞争也可能不同。保留两次结果，再补
较低负载，比挑选其中较好的一次更能支持下一步决策。

反向复测可以减轻固定顺序带来的偏差，但不能彻底消除它。更严格的研究可以采用
更多独立重复、随机化或完全平衡的顺序，并额外监测主机竞争。

## 4. 参数化为什么还需要“配置指纹”

现在可以选择负载、控制器、负载模式和重复次数，不必每次改脚本源文件。
例如下面的命令只打印计划，不会访问集群：

```bash
RPS=25 BENCHMARK_PATTERNS=step \
BENCHMARK_CONTROLLERS='native_hpa_60 phpa' BENCHMARK_REPEATS=3 \
  bash hack/run_matrix.sh --dry-run
```

但能修改参数还不够。假设昨天的 `step/phpa/r1` 使用 25 RPS，今天改成 40 RPS，
仅凭同一个实验名称就跳过，会把旧结果误当成今天已经完成。

配置指纹记录有效负载、并发数量、集群上下文、镜像、时间表和相关源码等身份。
续跑只有在这些条件匹配、且提取结果有效时才跳过。提取失败会停止当前矩阵，
保存失败原因和原始数据；下一次尝试使用新目录。这样既方便中断后继续，也能
防止不同配置的结果悄悄混在一起。

它不能代替环境检查：同一个集群名称背后的应用镜像或资源配置可能改变，所以
实际运行前还要保存并核对集群快照。

## 5. 为什么固定 60 秒窗口，并交替运行两种控制器

两组匹配副本范围 1–10、CPU 目标 50%、应用镜像、资源配置和 60 秒缩容稳定窗口。
这里的 CPU 目标按 Pod 的请求量计算：200m 请求量的 50% 对应每 Pod 约 100m，
也就是 0.1 个 CPU 核。
如果一组用 300 秒窗口，另一组用 60 秒，那么资源拖尾的差异可能来自窗口长度，
不能直接算作预测算法的效果。

三组配对顺序是 Native/PHPA、PHPA/Native、Native/PHPA。交替顺序有助于减轻
缓存、主机状态随时间变化的影响，但三组并非完全平衡，也不足以宣称统计显著。
这轮用来检查结果是否可复现、差异大致在哪；完整统计研究需要进一步设计。

两者仍有指标来源、采样、实际协调频率和伸缩策略的差异。因此这轮比较的是
完整控制器。若以后要隔离“预测”本身的作用，需要在同一个控制器中切换预测
与非预测决策，并控制其余流程。

## 6. 为什么资源比较要统一起点和终点

假设一组准备控制器花了 20 秒，另一组花了 60 秒。把准备阶段也算进资源成本，
后者就会先多出 40 秒的占用，哪怕负载开始后的扩缩容曲线完全一样。

新统计从负载开始算起，结束于计划停止发压后 360 秒。step 的共同窗口为
541 秒，开头的 30 秒静默、编译、启动和文件收集耗时不扩大这个比较窗口。
原来的统计字段仍然保留，新结果使用单独的 `measurement` 字段。

360 秒是较保守的尾部长度，能覆盖更长的资源拖尾，但会增加实验耗时。提前选定
更短窗口可以节省时间，也更容易出现尚未缩容完成就停止观察的截断。本轮不会
根据已经看到的曲线中途缩短窗口。

**Pod-seconds 是副本数随时间的积分。** 例如 1 个副本运行 60 秒，再用 3 个副本
运行 40 秒，共是 `1×60 + 3×40 = 180 Pod-seconds`。它描述副本占用时间，
不等于 CPU 消耗，也不直接等于云账单。

本轮副本数据每 15 秒采样，两个采样点之间沿用前一个值。因此首次扩容是首次
“观察到副本增加”的时间，资源积分也是采样估计。超过 15 秒的观测缺口会让
新测量无效，不能用缺失数据拼出一条看似完整的曲线。

## 7. 怎样阅读最后的结果

把成功率、延迟、首次扩容、峰值副本和 Pod-seconds 放在一起看：响应改善可能
需要更多资源，资源减少也可能伴随更差的服务表现。还要检查单次结果、波动、
丢弃迭代，以及观察结束时是否已经缩回最小副本。

如果 PHPA 首次扩容较晚，可以进一步核对输入与决策日志。当前实现使用
一分钟 CPU rate、EWMA 平滑和阻尼趋势外推；平滑有助于抑制噪声，也可能延缓
突变响应。具体原因要由本轮日志支持，不能仅凭算法名称或一张曲线下结论。

本轮就有一个具体记录：PHPA 第二次运行在负载开始约 29 秒时，当前 CPU 为
98.65%，预测为 52.87%，目标为 50%。预测值落在目标附近的容差带里，因此这次
判断没有扩容。这能说明一次决策是怎样发生的，但不能把全部成功率差异都归因
于预测；指标来源和调度时机等差异仍然存在。

完成这轮工作的标准是形成可追溯、能解释局限的证据。结果可以支持优势，也可以
暴露没有优势或存在代价的场景；这两类结果都能帮助确定是否值得修改算法。

回归测试和真实实验也各有分工：前者验证配置、续跑、统计和控制逻辑是否按预期
工作，后者观察它们在真实负载与环境中的效果。全部测试通过，并不保证预测方案
在业务指标上更好；仅有一次集群实验，也不足以替代可重复的逻辑检查。
