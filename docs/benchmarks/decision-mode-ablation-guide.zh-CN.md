# 为什么这轮先研究“用哪个信号扩容”

这轮把问题收窄到一个可验证的选择：预测值暂时低于当前需求时，控制器是否应该
允许当前 CPU 推动扩容？当前代码增加了三种决策模式、对应的回归用例和日志分析，
实验按[同控制器消融协议](decision-mode-ablation.md)安排。它们用于检验假设，
还不能证明混合模式改善了服务或节省了资源。

## 1. 从一次具体决策开始

[上一轮报告](capacity-and-controlled-pilot-20260906.md)记录了负载开始约 29 秒时的
一次判断：当前 CPU 为 98.65%，预测约 52.87%，目标为 50%。这里的百分比以 Pod
申请的 CPU 为基准。50% 目标的 10% 相对容差带约为 45%–55%，预测落在其中，
因此这次没有扩容。容差本来用于避免小幅波动反复触发伸缩，却也可能掩盖预测
尚未追上的需求突变。

回归用例用每 15 秒一个点、五分钟安静历史后突然升到 98.65% 的合成序列，
在 alpha=0.3、预测视野 30 秒时产生约 52.86% 的预测。它复现的是同类决策，
不是逐点重放上一轮全部指标。一个副本按当前值计算，应得到
`ceil(1 × 98.65 / 50) = 2`；按预测判断则仍受容差保护。

先抓住这个例子的好处是能说明改变针对什么。直接反复修改 alpha，可能找到更好
的一次结果，却仍分不清改善来自减少平滑滞后，还是改变了其他阶段的资源占用。

## 2. 三种模式只切换决策信号

令 `C` 为最新 CPU 观测，`F` 为已经限制在 `0` 到 `1.3×C` 内的预测，`T` 为目标：

| `spec.decisionMode` | 送入共同副本公式和容差规则的信号 |
|---|---|
| `Predictive` | `F`；省略字段也采用此模式，保留已有行为 |
| `Current` | `C`；提供同一套控制流程中的观测值基线 |
| `Hybrid` | `max(C, min(F, T))` |

Hybrid 先把预测最多压到目标，再与当前值取较大者。因此预测自己不能推动扩容，
也不能把决策信号压到当前需求以下。上面的 98.65% 场景中，它选择当前值。

负载下降时，假设已有五个副本，`C=30%`、`F=39%`、`T=50%`，Current 的基础
建议是三个副本，Hybrid 是四个，给回落留一些余量。若 `C=44%`、`F=57.2%`，
Hybrid 选择 50%，保留五个副本，避免预测单独要求增加副本。这些是规则示例；
最终还要经过共同的上下限、稳定窗口和容差，不能把基础建议直接当成实际动作。

三种模式都保留预测计算和预测状态列，也共用样本就绪条件：至少两个有效样本。
Current 因而仍可能等待历史数据，也仍使用带采集和一分钟 CPU rate 窗口延迟的
观测。这样能把比较集中在信号选择上；若让 Current 跳过等待，就又改变了冷启动
流程。后续可以单独研究这种优化。查看实际决策应结合日志中的模式和决策信号，
不能只看仍在展示的预测列。

## 3. 为什么用同一控制器和公开接口测试

原生 HPA 与 PHPA 的对比同时包含指标来源、协调时机和伸缩策略等差异。即使
缩容窗口相同，也不能把全部服务差异归给预测。这次让三个模式使用同一二进制、
指标提供器和控制流程，相当于只换一个开关，解释结果会更直接。

测试先行的顺序是先规定可观察行为，确认旧实现无法满足新增要求，再实现并做
回归。这里通过 envtest 创建 Deployment 和 PHPA，运行真实协调器，再读取副本
请求和状态；只在外部指标接口注入可控序列，并用可控时钟检查稳定窗口。用例也
覆盖默认值、非法模式、Hybrid 的方向保护及副本边界。执行是否通过必须以测试
日志为准，写好用例本身不等于已经完成验证。

这种方式能检查 API 默认值、配置是否接入以及 Scale 写入等环节。只测一个选择
函数更快、边界枚举更便宜，却可能漏掉“函数正确、控制器没有使用它”的错误。
envtest 的代价是需要 API server 和 etcd；它也不运行真实 Pod、流量和完整集群
调度，因此不能代替负载实验。

## 4. 怎样比较动作、服务与资源

控制器现在在 Scale 写入成功后记录 `Scaled Deployment`。判断是否真正提高了
请求副本数，要比较新值与写入前的 `previousDesiredReplicas`：例如目标已经是
三个、观测状态仍是一个，再次写入三个不算一次新的扩容请求。日志时间与每
15 秒采样首次看到副本增加的时间分别报告；两者都不能直接代表新 Pod 已开始
承接请求。

实验固定 25 RPS step、1–10 副本、50% CPU 目标和 60 秒缩容窗口；运行前核对
此前容量校准的镜像、资源及环境是否仍匹配。三轮依次采用
Predictive/Current/Hybrid、Current/Hybrid/Predictive、Hybrid/Predictive/Current，
让各模式各占一次第一、第二、第三位置，并检查轮间恢复。

每次保留 30 秒静默期；资源统计从负载开始到计划停止后 360 秒，共 541 秒。
统一窗口能避免准备、请求排空和复制文件的耗时污染比较。Pod-seconds 是副本数
随时间的积分，不等于 CPU 消耗或账单；15 秒采样也带来时间和积分误差。

HTTP 200 比例、全请求 p95、成功请求 p95、未发出的迭代、首次扩容及资源占用
要一起看。少用副本若伴随更多超时，不能称为效率收益。失败、超时和异常尝试
都应保留；看到中间结果后调整参数或只重跑差的一组，会破坏预先约定的比较。

## 5. 为什么暂时不扩大模型和参数搜索

先切换信号选择，实验成本较低，也能直接检验已观察到的抑制路径。扩大 alpha
搜索会增加实验数量和挑选偶然好结果的机会；若这轮确认平滑滞后值得优化，再
固定评估标准，并用独立负载验证参数，会更有依据。

Holt、ARIMA 或更复杂模型适合在已确认存在可利用趋势、周期或充足历史数据后
研究，但需要额外的参数估计、数据和验证。它们也不能自动消除采样延迟和 Pod
启动时间。Hybrid 自身有明确取舍：它放弃由预测单独提前扩容，回落时保留余量
也可能增加资源拖尾，是否值得必须看实测。

三次重复、单一种类负载和共享主机仍只支持描述性结论。平衡顺序不能消除前一轮
残留和主机竞争；测试通过只能支持规则按预期执行，不能推出服务优势。
