# 同输入决策回放与扩容等待分析：2026-09-11

我对 [9 月 10 日的 18 次正式 warm 运行](live-baseline-20260910.md)做了离线回放。结果把首次扩容较晚分成了两种已有证据支持的情况：三次 step Predictive 已经看见较高的当前 CPU，但预测信号和容差规则没有允许写入；另外两次 step Hybrid 的当前输入仍低于目标，同输入切换三种模式都不会在那一轮扩容。

这次完成的是规则解释与证据核对。回放固定真实记录的 CPU 输入和副本状态，没有模拟提前扩容后 CPU 如何变化，也没有产生新的 HTTP 成功率、p95 或副本时间结论。本轮保持默认模式、30 秒协调周期、60 秒 CPU rate 窗口和安全规则；分析不需要 Docker、WSL 或新集群。

## 回放覆盖与证据强度

| 项目 | 本轮结果 | 如何解释 |
|---|---:|---|
| 正式运行 | 18 | step、ramp 各 9 次，仍是每个负载与模式组合 n=3 |
| 完整协调周期 | 906 | 从每个 controller 启动开始，包含暖机与拒绝观测 |
| 有效 CPU 观测 | 625 | 其中 18 次仅有首个历史样本，尚未生成决策 |
| 可回放决策 | 607 | 全部原模式决策匹配记录 |
| 完整 CPU 历史重算 | 457 | 重新执行现有 Go 预测器，再核对原模式策略 |
| 沿用记录预测值 | 150 | 历史中仍有一个未记录的初始 CPU 值，只核对后续策略 |
| 成功 Scale 写入 | 98 | 包含扩容和缩容，逐项核对写入前后的请求副本链 |
| Deployment API 读取核对 | 6,375 | 请求副本与写入链一致，并检查目标与 PHPA 身份及配置 |
| 被拒绝的观测 | 281 | 查询前 175 次、查询后 106 次，没有将其伪装成有效决策 |

旧报告的 571 条决策从 warm gate 的观察范围开始计数；这里为重建预测历史和缩容稳定历史，保留了启动以来的完整前缀，多出 36 条暖机决策，得到 607 条。两者统计范围不同，没有增加新的正式运行。

旧日志没有输出第一次有效观测的 CPU 数值。这个未知值尚在五分钟历史窗口内时，我使用 `recorded-forecast` 标记；直到未知值过期、返回历史中的每个 CPU 值都能从记录恢复，才标记 `computed-history`。不能用后来的预测结果反推初值，再宣称预测已独立验证。下文首次 step 决策均属于沿用记录预测值的范围，因此它们支持对信号选择与扩缩容规则的解释。

另一路仅使用 Python 标准库、不调用本轮生产分析器和 Go 回放函数的独立核对，也得到 906 个周期、607 条决策、98 次写入及 6,375 次 API 读取，记录不一致为零。它重新核对了可恢复历史的预测算术、持续历史锚点与临时返回尾部的区别，以及请求副本链。这是数据一致性证据，不会把统计样本量从每组 3 次变成 607 次。

代码检查、Linux envtest／race、命令行回归、独立审查和已修复问题见[验证记录](decision-replay-validation.md)。

## 已看见高 CPU，但这一轮规则没有允许扩容

以下时间都以该次负载实际开始为零点。三次 Predictive 的首轮当前副本与请求副本均为 1，CPU 目标为 50%。`finalDesired` 是策略给出的最终目标，是否允许写入还要检查 `skipReason`。

| step 运行 | 首轮决策（s） | 当前 CPU | 记录预测 CPU | Predictive 回放 | 同输入 Current／Hybrid 回放 | 实际首次 Scale 增长（s） |
|---|---:|---:|---:|---|---|---:|
| Predictive r1，`183937` | 28.457 | 77.23% | 42.86% | 目标 1，`DesiredEqualsCurrent` | 目标 2，无跳过原因 | 58.482 |
| Predictive r2，`190231` | 28.474 | 90.08% | 49.98% | 目标 1，`DesiredEqualsCurrent` | 目标 2，无跳过原因 | 58.518 |
| Predictive r3，`195936` | 28.443 | 91.28% | 50.65% | 目标 2，`WithinToleranceBand` | 目标 2，无跳过原因 | 58.474 |

前两次预测值尚未超过目标，公式得到一个副本。第三次 `ceil(1 × 50.6541 / 50)` 已得到两个副本，但决策 CPU 与目标只相差约 1.31%，落在现有 10% 容差带内，因此没有写入。只看 `finalDesired=2` 会把这次决策误读为已经扩容。

同输入比较说明：对这三次真实记录的首次决策，Current 和 Hybrid 都会给出可执行的扩容建议，而 Predictive 会等待。实际三次运行都在下一次约 30 秒后的协调中写入 Scale。这个结论解释的是特定决策；它没有证明如果当时换成 Current 或 Hybrid，后续也会经历原有 CPU、副本数和 HTTP 结果。

完整示例见 [Predictive r3 输入](assets/decision-replay-20260911/20260910_195936_step_phpa_r3/replay-input.json)、[三模式结果](assets/decision-replay-20260911/20260910_195936_step_phpa_r3/replay-result.json)和[时间线报告](assets/decision-replay-20260911/20260910_195936_step_phpa_r3/report.json)。

## 输入仍低时，更换模式也没有消除本轮等待

| step Hybrid 运行 | 首轮决策（s） | 当前 CPU | 记录预测 CPU | 接受观测时的源样本年龄（s） | 同输入三模式结果 | 实际首次 Scale 增长（s） |
|---|---:|---:|---:|---:|---|---:|
| r1，`185104` | 28.430 | 0.68% | 0.39% | 28.02 | 均目标 1、跳过写入 | 58.461 |
| r3，`193647` | 28.437 | 33.66% | 18.68% | 21.74 | 均目标 1、跳过写入 | 58.478 |

这两次已经能排除“当前输入越过目标，Hybrid 却选择较低预测值”这一解释。另一轮 Hybrid r2 的首轮 CPU 为 56.46%，在 28.484 秒实际写入，行为与规则一致。

九次 ramp 首轮决策均约在 28.4 秒，当前 CPU 为 0.42%–41.98%，全部低于 50% 目标；同输入三模式均未给出可执行的扩容建议。它们的实际首次 Scale 增长在 58.399–58.598 秒。这没有显示在那些首次输入上，只改模式就能得到提前扩容。

源样本年龄表示“接受观测时刻减去记录的源样本时间”。它有助于发现输入可见性的差别，但不能确定 cAdvisor 何时刷新了缓存、Prometheus 一次 scrape 的精确起止，或负载的变化何时完整进入 60 秒 rate 结果。现有记录也没有采到两次协调之间所有可能的有效输入，不能把那段等待全部归到指标系统或协调计时器。

## 一条时间线如何拆开等待

以 step Predictive r3 为例，报告保留了下列实际边界：

| 事件 | 相对负载开始时间（s） | 可支持的结论 |
|---|---:|---|
| 首轮使用的源样本时间 | 12.101 | 这是记录的源样本时间 |
| 首轮查询开始／结束 | 28.434／28.438 | 该次查询请求约耗时 4 ms |
| 首轮观测完成 | 28.442 | 该时刻源样本年龄约 16.34 s |
| 首轮决策 | 28.443 | CPU 91.28%，预测 50.65%，命中容差而跳过 |
| 下一轮决策 | 58.470 | 得到允许写入的扩容建议 |
| 成功 Scale 响应 | 58.474 | API 接受副本请求的真实边界 |
| 首次 Ready 增长观察范围 | 59.075–61.117 | 增长只能由前后有界 API 读取约束 |

第一轮到下一轮之间，前一次协调结束到下一次开始约 30 秒。这个字段在报告中叫 `unobserved_since_previous_finish_seconds`，描述没有协调日志覆盖的区间，不能直接称为“浪费的时间”。期间是否出现足以触发扩容的新输入，还需要后续实验采证。

906 个周期的解释分类总和如下。每个周期只有一个优先分类，例如成功写入优先归为 `scale_written`；它不是互相独立的原因效应分解。

| 分类 | 次数 |
|---|---:|
| 当前输入不高于目标 | 359 |
| 查询前拒绝观测 | 175 |
| 缩容稳定规则保留目标 | 137 |
| 查询后拒绝观测 | 106 |
| 成功 Scale 写入 | 98 |
| 历史仅有一个样本 | 18 |
| 其他目标未变化 | 8 |
| 容差带跳过 | 3 |
| 较低预测未触发扩容 | 2 |

281 次拒绝中，原始错误类别为 279 次 incomplete data、2 次 target changed during observation。查询前拒绝与查询后拒绝用日志中的查询边界区分，因此不能把 906 个协调周期都当作 Prometheus 查询次数。这些次数也不是拒绝持续的秒数；密集事件可能在很短时间内产生多次拒绝。Ready 增长同样只有读取边界，不能由它推断新 Pod 第一次处理请求的时间。

## 我接下来要验证的一个假设

我会优先检验：**固定 Current 模式及其他规则，把协调间隔从 30 秒改为 15 秒，只有在新增的协调机会能读到可用的新信号时，才可能减少首次扩容等待；若读到的仍是旧值或被安全检查拒绝，主要变化可能是查询开销。** 本报告只提出实验，不执行新的在线批次。

下一轮先在独立 Kind 环境完成 Service 分流和固定副本容量校准，再做三个配对、共六次 step pilot。CPU rate 保持 60 秒，scrape 保持 15 秒，目标、副本范围、工作负载、容差、身份校验、缺失指标规则和 warm 条件保持一致；唯一处理变量是 30 秒与 15 秒协调间隔。

负载起点相对“已观察到的新源样本”的偏移按相同容差配对，同时保留实际偏移及样本时间。这样可以减小两轮负载恰好落在不同输入相位的影响，但仍不把这个锚点称作 cAdvisor 刷新或 scrape 的精确时刻。配对内交替运行顺序，所有已分配结果和失败回执都保留。

比较时同时记录实际协调相位、有效新观测数量、拒绝观测的有界持续时间、真实查询数量、首次 Scale／Ready 边界、HTTP 成功率、全请求 p95、丢弃迭代以及请求／Ready 副本时间。先看额外的协调是否真的拿到了新信息，再看服务结果是否改善及付出了多少副本和查询开销。六次 pilot 只能帮助检查机制和后续实验设计，不足以证明生产收益；本轮也没有预先承诺 15 秒更好。

## 复现范围

公开的[紧凑证据目录](assets/decision-replay-20260911/)按运行保留 `replay-input.json`、`replay-result.json` 和 `report.json`。报告中含原始文件的字节数、SHA256、目标身份和配置来源。只使用紧凑输入即可重新运行 Go 回放；要重新核对原始日志、API 读取、负载起点和文件哈希，仍需本地保留的原始基线归档。

在仓库根目录执行以下命令，可以重放文中的第三次 Predictive step。它不会构造 Kubernetes 客户端或写入 Scale：

```bash
go run ./cmd/replay -input docs/benchmarks/assets/decision-replay-20260911/20260910_195936_step_phpa_r3/replay-input.json
```

拿到完整基线证据后，可以从原始 run 重新生成报告。`--output` 必须使用尚不存在的目录，以保留旧结果：

```bash
go build -o bin/replay ./cmd/replay
python3 -m pip install -r hack/analyze/requirements.txt
python3 hack/analyze/decision_replay.py benchmark-runs/live-baseline-20260910/verified-baseline/matched-step/runs/20260910_195936_step_phpa_r3 --output benchmark-runs/decision-replay-reproduction/r3 --replay-binary bin/replay
```

Windows 下可构建为 `bin/replay.exe`，将 `--replay-binary` 同步改成该路径，并使用已配置的 Python 命令。更完整的实现取舍、输出字段和验证边界见[中文讲解](decision-replay-guide.zh-CN.md)。
