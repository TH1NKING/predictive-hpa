## 红绿回归修复了什么

| 问题 | 红阶段观察 | 修复后的公共行为 |
|---|---|---|
| campaign 收到 SIGTERM | 进程直接以 `-15` 退出，未完成收尾 | 转入有界清理，保留失败状态，停止后续槽位 |
| verifier 的后代忽略 TERM | CLI 返回后，嵌套进程仍存活 | 对整个进程组发 TERM，必要时 KILL，并保留输出与终止回执 |
| 父进程正常退出、后代仍运行 | 正常父进程退出导致清理句柄丢失 | 检查剩余进程组，清理后将该命令记为失败 |
| 收尾期间再次收到终止信号 | 跳过 summary 和集群清理 | 在有界诊断、删除和写入回执期间延后处理信号 |
| 原始请求成组截断 | 四类请求指标计数仍相等，错误接受为完整数据 | 与 k6 独立汇总、完成时刻和退出回执交叉核对 |
| kubeconfig 别名指向错误集群 | 名称看似正确，仍可能进入首个槽位 | API 节点名单必须与指定 Kind 的实际节点名单完全相同 |
| 保留的 HPA 名称指向其他工作负载 | 可能被历史单轮入口按名称删除 | 在构建和发压前拒绝冲突，九个槽位均保持 `not_run` |
| Docker 返回 manifest ID、CRI 返回 config ID | 实际 Kind 加载后被错误拒绝，旧模拟夹具未覆盖空 repoDigests | 验证 manifest 原始字节 SHA256，再验证 config 引用、大小及内容 SHA256；只允许已证明关联的 Pod ID |
| 固定缓存包含当前平台、缺少其他平台 | Kind 的全平台导入因缺少 ARM64 内容而失败 | 读取实际节点平台导入，保留原索引和 digest；不声明验证了其他架构 |
| 复制成功但导入进程看不到容器内路径 | 实际导入报 `no such file or directory` | 从私有归档直接传入二进制 stdin，保留输入哈希和大小，所有退出路径关闭句柄 |

这些测试覆盖“何时允许开始”和“失败后如何停止”，没有要求算法必须扩容、必须跑赢其他模式，或必须达到服务标准。未扩容和服务失败都可以是有效的实验结果；缺失必要证据、身份不一致或清理失败则不能作为成功运行接受。
