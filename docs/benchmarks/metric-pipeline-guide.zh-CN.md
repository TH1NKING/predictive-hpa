# 从 CPU 采样到扩容信号：本轮实现与方法讲解

本文配合[实施协议](metric-pipeline-followup.md)解释观察器、分析方法与测试。
现场结果和最终取舍将在完成封存与独立复算后补充。

## 我们正在回答什么问题

预测控制器要根据输入作出决策。负载已经到来，但输入仍是较早的低 CPU 值时，
更复杂的预测也未必能及时反应。前一轮十次记录提示两个不同的问题：有时近期
CPU 已升高，一分钟表达式仍未超过阈值；但把窗口缩至三十秒又经常不够两个
源样本。这一轮要判断信息在哪里变慢，以及短窗口实际能否持续返回结果。

可以把过程写成：

```mermaid
flowchart LR
  A[工作负载消耗 CPU] --> B[cAdvisor 暴露带时间戳的计数器]
  B --> C[Prometheus 抓取与解析]
  C --> D[样本进入可查询存储]
  D --> E[30 秒与 60 秒 rate 求值]
  E --> F[控制器下一次查询与决策]
  F --> G[提高目标副本]
```

这张图描述处理顺序，不表示我们已经精确测出每一个箭头的耗时。尤其是单个
样本的内核统计时刻、内部更新完成时刻和 TSDB 提交完成时刻，不能仅靠外部
请求时间推算。

## 实现怎样把证据串起来

生产控制器继续使用一分钟 CPU rate。新增功能由实验开关启用，放在旁路观察器
中。观察器每轮选择一个求值时间，再把同一时间传给原始 counter、CPU request、
三十秒与六十秒表达式。每条结果都有轮次编号、求值时间、请求开始与结束、
响应原文或错误。统一求值时间减少比较中的一个变量；请求分别执行，仍可能
看到不同的存储状态。

源端证据来自节点的 `/metrics/cadvisor`，通过现有 Kubernetes node proxy 只读
访问。只保留本次应用的 CPU counter 和 `container_last_seen` 行。源端的 CPU
timestamp、请求时间、`container_last_seen` 的值分别记录。预检已经确认，CPU
行的显式毫秒时间戳与同次 last-seen 时间并不相同。后者不能当作 CPU 的更新
时刻，源端读取本身也不能冒充 Prometheus 的一次抓取。

这也能从对应上游实现解释：Kubernetes 1.35.0 依赖 cAdvisor 0.53.0；该版本
CPU counter 使用统计对象的 `s.Timestamp`，last-seen 则在导出时读取当前时钟。
所以“容器刚刚被 exporter 看见”与“CPU 统计刚刚更新”是两回事。
参考：[Kubernetes 依赖版本](https://github.com/kubernetes/kubernetes/blob/v1.35.0/go.mod#L32)、
[cAdvisor 导出逻辑](https://github.com/google/cadvisor/blob/v0.53.0/metrics/prometheus.go#L119)。

抓取证据有两路：targets API 提供最近抓取的报告时间、耗时、健康状态与错误；
`up` 和抓取耗时、样本数的原始时间序列补充两次轮询之间已保存的记录。它们
帮助区分“源端没有新样本”和“抓取发生异常”，但没有保存的尝试仍然未知。

本轮实际运行 Prometheus 3.11.3，配置 `honor_timestamps: true`。核对该版本源码
后有两个需要小心的细节：报告的抓取时间可能经过轻微对齐；targets 状态在
TSDB 提交之前更新。因此 `lastScrape + lastScrapeDuration` 不能称作精确入库
时间，`up=1` 也不能单独证明该样本已经可以查询。
参考：[抓取循环与提交顺序](https://github.com/prometheus/prometheus/blob/v3.11.3/scrape/scrape.go#L1217)、
[目标状态字段](https://github.com/prometheus/prometheus/blob/v3.11.3/scrape/target.go)。

## 为什么必须执行真实 rate

两个 counter 样本相减再除以时间，只得到该区间的平均 CPU 核数。Prometheus
的 `rate` 还处理计数器重置和窗口边界外推。旁路执行真实表达式，才能观察当前
引擎究竟返回一个数、空向量还是错误。
参考：[rate 定义](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate)。

原始样本数和表达式返回值同时报告。三十秒窗口的计数边界是左开右闭：
`evaluation - 30 < sample timestamp <= evaluation`。恰好位于左边界的样本
不计入；缺少样本不补零。CPU 为零意味着真实观测为零，空结果意味着缺少一个
可用结果，控制上的意义不同。

## 为什么只分析首次扩容之前

扩容之后，新 Pod 会分担请求，CPU 分母与参与计算的序列也会变化。如果把这些
观察混入“首次信号为什么晚到”的比较，就引入了控制动作的反馈。

主分析从实际 k6 场景负载起点开始，截止于首次成功提高目标副本的 Scale 写入
开始。观察请求必须在这个截止点之前已经返回。以成功日志确认动作，再以该
日志记录的写入开始切断输入，是为了避开写入期间已经出现变化的情况。没有
扩容时，终点保留未知，不能把整场记录重新命名为扩容前证据。

## 测试怎样约束容易出错的地方

测试从公开 CLI 和输出文件观察行为。观察器测试使用本地 HTTP 服务和外部命令
替身提供可控响应；分析测试使用可手算的原始记录。每个新增行为先出现失败，
再实现到通过，使测试证明它能识别一个真实缺口。

关键行为包括：共享求值时间；保留空值与查询错误；源端 timestamp 不被请求
时间覆盖；窗口左边界；截止点过滤；配对缺失或时间不一致；重复与歧义样本；
没有扩容时仍拒绝损坏输入；输出不能覆盖原始证据。

测试能证明程序怎样处理这些输入。真实三次运行再由一份不导入主分析器的程序
复算关键数字，减少主程序与验证程序共享同一错误的风险。两者一致仍不能消除
实验设计中的混杂因素和没有采到的数据。

## 方法取舍

| 方法 | 能解决什么 | 主要代价或不足 |
|---|---|---|
| 本轮源端与多窗口旁路观察 | 将源端、抓取和表达式放到可比较的时间线上 | 额外查询会增加负担，观察本身不证明修改控制后的效果 |
| 立即把 CPU 窗口改成 30 秒 | 直接获得改变控制动作的结果 | 样本不足时容易增加空结果，且当前缺少可靠的参数依据 |
| 只缩短协调间隔 | 减少等待下一次查询的机会 | 上游尚未产生新信息时，更多查询仍会读到旧值 |
| 只做 counter 差分 | 简单、可手算，适合看近期增量 | 不等于 Prometheus rate，不能替代窗口候选的实际结果 |
| 结束后再查询历史数据 | 低干扰、适合检查最终存储内容 | 无法还原当时第一次何时可查询 |
| 同时改采集、窗口和预测算法 | 可能很快看到不同的服务表现 | 无法可靠判断哪个改动造成差异，难以复现与选型 |

本轮先做两次固定副本校准，再做三次相同 Current 配置观察。最近节点重启使
旧的校准不能直接当作当前环境已验证。校准与控制器实验分别保存，三次重复
提供可行性证据，不足以推断普遍收益或统计显著性。

若三十秒窗口有稳定、持续更早的有效信号，后续才值得只改变 CPU 窗口做闭环
对照，衡量 HTTP 成功率、全请求 p95 与 Pod-seconds。若样本或归因仍不充分，
保留当前默认值也是一个有证据的结果。
