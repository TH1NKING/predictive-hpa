# 协调周期 pilot：工具验证与审查记录

本记录覆盖 `cadence-pilot-v1` 的观测、启动 gate、编排和分析工具。审查固定基线为 `42eff31`，实现版本为 `59e12f2`。实验约束见[配对方案](cadence-pilot-plan.md)，实现理由和结果读法见[中文指南](cadence-pilot-guide.zh-CN.md)。

这里区分两类证据：测试说明工具是否遵守约定；真实集群运行才提供协调周期对扩容、服务和成本的影响。[六轮真实结果](cadence-pilot-20260914.md)已完成，但有效配对为 0，不能据此认定 15 秒优于 30 秒。

## 验证范围

| 环境／阶段 | 已完成的检查 | 结果与边界 |
|---|---|---|
| Linux validation04 | `make lint-fix`；`GOFLAGS=-race make test`；Python 分析与 harness 全套 | Go 1.26.2、envtest Kubernetes 1.35；全部通过。分析 105 项；harness 103 项，其中 4 个 Node 用例因运行环境缺少 Node 跳过。没有生成或格式化文件变化 |
| Linux validation05 | Python 分析与 harness 再验证；源码身份核对 | 分析 105 项、harness 104 项通过，其中同样跳过 4 个 Node 用例；Go 文件与 validation04 逐字节一致；核对的全部 366 个文件与 `59e12f2` 匹配 |
| Windows 全套 | Python 分析与 harness | 分析 105 项、harness 99 项通过；harness 中 6 个 POSIX 专用用例跳过。Windows 结果用于离线工具行为验证 |
| Windows 后续定向验证 | observe 相关 11 项，包括 4 个请求进行中／部分日志场景和 Pod 延迟出现用例 | 通过；这是定向补验，不代表 Windows 重新运行了最终 104 项 harness 全套 |
| Node 工作负载边界 | 4 个 Node 用例在 Windows 执行 | 通过；核对脚本负载形状、请求参数和实际 scenario-clock 记录 |

Linux 的 race 与 envtest 结果来自真实 Linux 进程和临时 Kubernetes API／etcd。它们不替代独立 Kind 的负载实验，也不构成吞吐或延迟改善结论。validation05 复用的是逐字节相同 Go 文件在 validation04 的结果，其新增验证范围是 Python 工具及最终源码身份。

## 红→绿覆盖了什么

| 边界 | 失败用例要求证明的行为 | 最终处理 |
|---|---|---|
| 生产 CPU 观测与 HTTP | 记录真实请求、完整响应体读取耗时、POST 405 后的 GET 回退，以及首次 CPU 观测 | 在 transport 层保留每次请求回执；观测成功与单次 HTTP 尝试失败分别记录，不用固定查询倍数推算 |
| 并发测试夹具 | race 检查能暴露 HTTP handler 与夹具修改之间的竞争 | 在启动 `httptest.NewServer` 前冻结夹具数据，消除测试夹具自身竞态后重新验证 |
| 完整容器源时间 | 相同成员集合中每个容器都必须出现严格更新的源样本 | 拒绝成员变化、部分更新、旧／未来样本；保留完整容器身份与前后观测 |
| 初始观测与损坏输入 | 缺失或损坏的源时间不能伪装成有效初始输入 | 保持错误或未知，不用零值补出一个可用样本 |
| 进行中的观测与日志 | gate 不能把未结束请求或写入到一半的记录当作完成证据 | 对进行中请求和部分日志增加边界回归；完整非法记录仍失败，未完成尾行不参与选锚 |
| k6 Pod 启动顺序 | runner 计划文件存在时，Pod 可能尚未创建 | 从真实 `PodNotFound` 失败定位到创建窗口；增加有界等待 Pod Ready，再启动本轮控制转发 |

测试通过公共 CLI、HTTP、Kubernetes 接口及工作负载执行边界验证行为。失败回执保留；修复后的通过结果没有覆盖原失败记录。

## Standards

固定基线审查没有剩余阻断问题。一个非阻断建议已接受保留：六槽位分配约束在 campaign、shell 配置校验和分析器中存在重复。当前保留各公开入口的独立校验，防止直接调用其中一个入口时绕过协议；这些分配必须随协议版本共同维护。

## Spec

工具与协议实现审查没有剩余问题。覆盖项包括唯一周期变量、完整源样本 gate、真实查询计数、暂停后的 k6 放行、失败槽位保留、身份与清理检查、实际负载时间，以及配对有效性和服务准则的分别报告。

工具审查与真实实验分别验收。服务不达标仍可能是完整的实验结果；证据缺失、身份错误或相位不合规则影响比较资格，不能通过删除不利运行解决。

## 真实运行状态

首批第 1 槽在 gate 放行前因 k6 Pod 尚未创建导致控制转发失败，后续 5 槽保持 `not_run`。原分配和失败材料已保留；恢复检查确认 gate 未放行、HTTP 请求为零，并使用捕获 UID 与 resourceVersion 条件清理该槽所属资源。

第二批六轮全部完成，独立原始记录审计差异数为 0。六轮单独的证据覆盖与相位均合格，启动相位误差均小于 0.03 秒；三个配对的源样本年龄差为 3.430000、1.898000、1.299999 秒，都超过冻结的 1 秒门槛，有效配对为 0。分析保留全部原值，没有生成有效配对差值，也未把服务失败删出结果。

专用 Kind 集群与私有 kubeconfig 已清理，共享集群 UID 未变化。首批失败与恢复记录、第二批六轮证据继续保留。具体服务、Scale／Ready 边界、副本秒和查询开销见[结果报告](cadence-pilot-20260914.md)。

本轮证明了启动和留证协议能够执行，同时暴露了输入年龄的配对限制；0 个有效配对不证明 15 秒无效。下一版应预先改进源样本年龄对齐方法，保持门槛后再验证，不能直接据此调整默认配置。
