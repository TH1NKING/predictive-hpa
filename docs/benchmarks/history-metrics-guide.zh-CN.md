# 历史保留与指标延迟：实现和方法讲解

本次先处理控制器长期运行时的历史保留，再利用已封存的十次实验观察指标信息。
完整范围与验收见[任务说明](history-metrics-followup.md)，指标解释规则见
[分析协议](metric-visibility-diagnostic.md)。

## 稳定窗口保存的是什么

稳定窗口保存的是每轮计算的副本建议。假设一分钟内先建议 8 个副本，后来因为
CPU 暂时降低只建议 3 个，控制器会使用窗口里的最大建议 8，延后缩容。
这段历史只需要覆盖当前配置的时间窗口；已经过期的建议没有继续保留的必要。

原实现每轮都追加建议，却只在准备缩容时调用带有清理作用的窗口查询。
长时间保持副本数、尤其一直达到最大副本数时，旧建议会随运行时间累积。
缩短协调间隔又会增加单位时间内的记录量，因此先处理这个确定的工程问题。

修复将“维护有效历史”和“是否采用历史最大值”区分开：每次有有效决策时
都清理过期记录；只有建议缩容时才用窗口最大值保护副本。窗口边界仍然包含
恰好位于 `now - window` 的记录。

记录量由窗口内发生的决策次数决定，不能简单承诺“60 秒窗口永远只有 4 条”。
资源事件可能在正常重排队之外触发协调。窗口配置增大也不能重新找回此前已经
过期并清理的记录；控制器重启丢失内存历史的问题仍需另外设计。

## 为什么这样验证

测试通过真实 envtest API Server 创建资源，并检查公开的副本写入和诊断日志。
FakeClock 只推动稳定窗口所使用的策略时间，所以数分钟的保留问题可以快速、
确定地触发。日志中的策略时间单独命名，不与测量查询和 API 耗时的墙钟混用。

先运行旧代码让回归失败，再运行修复后的代码，是为了证明测试能识别这个问题。
仅看到新增测试通过，还不能确认它会在旧实现上抓住错误。

| 方法 | 本次取舍 |
|---|---|
| 每次决策维护现有窗口历史 | 改动小，清理与已有锁一起执行，容易保持缩容规则 |
| 给历史固定条数上限 | 条数不能直接代表时间；事件密集时可能提前丢掉仍有效的高建议 |
| 增加后台定时清理线程 | 需要额外处理同步、退出与清理相位，当前修复不需要这些机制 |
| 把历史写入 ConfigMap | 可以研究重启恢复，但增加 API 写入、冲突与恢复语义，不能代替过期清理 |
| 用真实时钟等待数分钟 | 验证更慢，容易受调度影响；这里需要验证的是窗口边界行为 |

## “当前 CPU”为什么也可能反应较慢

CPU 指标源保存的是累计使用的 CPU 秒数。当前配置使用一分钟 `rate()` 将累计量
变成每秒平均使用量，再除以 CPU request 得到利用率。因此，当前 CPU 不是一只
直接显示瞬时需求的仪表。[Prometheus 的 rate 定义](https://prometheus.io/docs/prometheus/latest/querying/functions/#rate)
还包含计数器重置处理和区间端点外推。

需要分别看三个过程：源样本的时间、查询何时看到该样本，以及一分钟表达式何时
超过扩容阈值。更频繁地协调可以增加读数机会，但不能自动生成尚不存在的样本。
更短的平均窗口可能更快响应，也可能更容易受噪声和样本不足影响；不能凭一次
相邻差分直接判断正式控制器应该改成哪个窗口。

## 为什么先重用原始证据

已有观察器保存了原始 counter、CPU request 和一分钟计算值，以及各请求的起止
时间。重用这些材料可以检查同一次负载下信息出现的先后，避免新负载与环境变化
混进最初的问题。六次时序实验和四次协调周期实验分别保留批次身份。

分析只取首次实际扩容写入开始前的证据，避免新增 Pod 改变 CPU 分摊后倒过来
解释第一次扩容。该限制也意味着，这次分析本身不提供更换窗口后的服务成功率。

如果一次查询尚未看到样本，下一次看到了，首次可见时间只能落在一个区间内。
前次查询的具体快照时刻未知，因此保守下界取其请求开始，上界取首次看到样本的
响应结束。并行的原始查询和 CPU 表达式查询也不能当作同一份原子快照。

相邻两个 counter 的差值除以时间差，可以告诉我们那个区间里 CPU 使用增长有多快。
它有直观、可手算的优点，但它没有实现完整 PromQL rate 算法。报告将它与实际
一分钟表达式分列，保留 reset、空结果和错误，不把缺失值填成 CPU 为零。

| 方法 | 能得到什么 | 当前不足 |
|---|---|---|
| 重算已有逐次观测 | 验证样本出现、近期增长和一分钟超阈值的顺序 | 不能拆出 cAdvisor、采集请求和入库各自耗时 |
| 只看实验后的历史查询 | 重建样本时间序列 | 不能还原当时首次可查询到的时间 |
| 用相邻 counter 差分 | 检查近期增长是否已明显上升 | 不等于短窗口 rate，更不是服务效果实验 |
| 匹配条件的窗口对照实验 | 测量修改窗口后的服务、资源及查询表现 | 需要新一轮冻结配置、环境校准和完整实验 |

## 这次实际学到了什么

历史回归先在旧清理逻辑上失败，再在修复后通过；三种模式的精确窗口边界也通过
验证。整个 Go/envtest 检查通过，分析工具的 55 项测试通过。

十次旧实验里，七次在同一轮观察中就看到了明显增量和一分钟 CPU 越过 55%；
另外三次，近期增量已经明显上升，一分钟 CPU 仍分别为 50.902%、54.135%、
47.020%，约 12、16、16 秒后才首次观测到越线。

这能解释为什么值得调查平均窗口，却还不足以马上缩短它。按当时保存的 200 个
raw 快照统计，30 秒窗口有 142 个不足两个样本，60 秒窗口只有 2 个。
采样稀疏时，缩短窗口可能使计算缺少输入。因此这次完成了修复和诊断，CPU 窗口
仍保留一分钟。计数是原始快照的样本充足性，不是修改参数后的实测失败率。

独立审计对主分析结果的 1616 项比较全部一致。完整十次结果、异常、时间线和
证据限制见[诊断报告](metric-visibility-20260908.md)。
