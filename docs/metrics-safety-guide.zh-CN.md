# 指标正确性、异常输入与重启保护：代码讲解

这次工作的目标是让扩缩容决策的输入和失败行为更可靠。它没有增加预测算法，也不代表预测已经带来性能收益。完整验收范围见[实现规范](metrics-safety-plan.md)，历史实验的版本边界见[实验导航](benchmarks/README.md)。

## 先区分两种历史

| 历史 | 保存什么 | 解决什么问题 |
|---|---|---|
| CPU 观测历史 | 通过身份、完整性和新鲜度校验的 CPU 百分比 | 给 EWMA 提供过去的需求信号 |
| 副本建议历史 | 应用稳定窗口之前计算出的建议副本数 | 防止短暂低值导致过早缩容 |

两者都在进程内，重启后都会丢失，但恢复方式不同：CPU 历史重新积累至少两个有效观测；副本建议历史丢失时，先保护目标当前已请求的容量一个完整窗口。

## 1. 为什么先修指标归属

旧查询使用 `pod=~"web-.*"`。`web` 和 `web-canary` 是两个不同的 Deployment，这个表达式却可能同时匹配两者的 Pod。此时即使 EWMA 和副本公式完全正确，也是在根据混入其他业务的数据做决策。

新路径先用 Deployment selector 缩小候选集合，然后通过 Kubernetes API 验证：

```text
Pod 的 controller owner UID
  → 当前 ReplicaSet UID
  → ReplicaSet 的 controller owner UID
  → 目标 Deployment UID
```

名称只用于查找对象，UID 用于判断是不是同一个对象。删除 `web` 后再创建同名 Deployment，会得到不同 UID，不能继承原目标的观测或保护状态。CPU 序列还必须匹配 Pod UID 和当前 runtime container ID，避免同一个 Pod 的旧容器实例混入本次计算。

查询前后各读取一次有效成员集合。若期间发生滚动更新、requests 改变、Ready 状态变化或容器重启，本次观测不参与决策，后续重新读取。Kubernetes API 和 Prometheus 没有跨系统事务，这个复核不能消除所有时间差，但能拒绝已经观察到的成员不一致。

## 2. CPU 百分比如何计算

`rate(container_cpu_usage_seconds_total[1m])` 的单位是 CPU 核：一秒消耗 0.1 CPU 秒，对应平均使用 0.1 核。分母来自同一组容器的 Pod CPU requests。

例如一个 Pod 有两个普通容器：

| 容器 | CPU 使用量 | CPU request | 单独利用率 |
|---|---:|---:|---:|
| app | 120m | 200m | 60% |
| helper | 20m | 100m | 20% |

整体利用率为 `100 × (120 + 20) / (200 + 100) ≈ 46.7%`。直接平均两个百分比会得到 40%，忽略两者 requests 不同。旧代码的 `avg(usage)/avg(requests)` 在成员完全相同时也能得到正确比值；问题在于两侧独立查询和过滤时，不能保证成员相同。

现在必须先对齐 `(Pod UID, container, runtime instance)`，确认每个容器有唯一使用量和正数 request，再求和。缺少 request 时不能简单跳过该容器，因为跳过会改变分母与业务含义。Kubernetes API 提供当前 requests，也避免了将实时使用量与另一次异步抓取的旧 requests 拼接。

普通多容器在支持范围内；Pod 级资源、可重启 init sidecar 等另有资源计算语义，本版本会明确拒绝。以后扩展时需要增加明确规则和对应验收。

## 3. 为什么改为积累实时观测

kube-state-metrics 的 ReplicaSet owner 指标没有 owner UID。仅凭历史 ReplicaSet 名称和当前对象，无法严格确认过去的 Pod 属于哪个 Deployment 实例；当前 Pod 列表也不能解释已经删除的历史 Pod。

因此 Provider 记录自己已经核验过的实时 CPU 百分比。滚动更新出现 Pending/未就绪的新 Pod，或新容器暂时没有 CPU 数据时，本轮不做决策，但此前已验证的观测仍按当时的成员保留在窗口中，不会用新 Pod 名单重新计算。缺失周期不补零，保留每次观测的真实时间。非法样本、源数据陈旧或查询报错则重新开始积累；这是对源链路故障的保守恢复策略。

这有明确代价：进程启动不能立即使用 Prometheus 中任意旧历史。所有模式都需要两个不同时间的有效观测，普通协调默认约 30 秒一次，观测间隔至少 15 秒。保留窗口支持 15 秒到 1 小时，但窗口必须容纳两个观测才能预测；目标缓存最多 256 个，逐出后需要重新积累。超过容量的持续活跃目标可能反复预热，本版本没有大规模可用性保证。

如果要跨重启完整恢复历史，可以持久化含 UID 的身份记录，或向 Prometheus 导出带完整 owner UID 的归属指标。这会增加持久化、清理和版本管理成本，当前选择先保证能够证明的输入范围。[ADR 0001](adr/0001-verified-live-cpu-observations.md)

## 4. 查询成功为什么还不够

HTTP 成功不等于数据可用。控制器还需要排除缺失容器、重复序列、旧 runtime 实例、NaN/Inf、负数以及陈旧的源样本。

Prometheus 表达式返回的时间通常是求值时间。今天执行一次查询，不代表参与计算的原始计数器也是今天刚采集的。因此额外查询原始 CPU 计数器的 `timestamp(...)`，逐个检查源样本年龄，默认上限为 45 秒；整个查询过程有 10 秒期限。这个时间证明的是 Prometheus 中保存的样本时间，不能证明 cAdvisor 刚刷新了内部缓存。

本版本选择简单保守的行为：有任何必要输入不可用，就保持 Scale，设置 `MetricsReady=False` 和具体原因，清除过时 CPU 展示值，保留上一次成功伸缩的时间。恢复有效观测后，状态和决策随之恢复。

另一种方案是模仿原生 HPA，对缺失 Pod 按扩容/缩容方向分别进行保守估算。这可以提高部分故障时的可用性，但需要完整的按 Pod 估算、Ready 处理和方向反转规则。本次先选“完整输入才决策”，代价是部分指标故障也可能阻止必要的扩容；不会将这种策略描述为原生 HPA 的等价实现。

## 5. 重启后如何防止立即缩容

假设目标已请求 5 个副本，控制器重启后第一轮观察到低 CPU，原始建议只有 1 个。旧代码没有建议历史，会直接允许缩到 1。新代码会保护这 5 个已请求副本一个完整稳定窗口，期间较高需求仍可以扩容。

这里必须读取 `Scale.spec.replicas`。Deployment 的观测副本数可能落后于已经提交的请求，不能因为 status 还没追上，就反向覆盖先前的伸缩动作。写入前再次校验 PHPA 和目标身份、配置及版本；Scale 和 status 是两个请求，后者失败不会抹去前者已经成功的事实。

保护状态同时记录 PHPA UID、目标 UID 和目标引用。同名重建、切换目标、改变窗口或时钟倒退时，会重新建立对应保护。缩短正数窗口也会保护一个完整的新窗口：旧时间桶聚合后无法还原每个峰值的精确时间，重新建立桶和保护能维持明确的边界。窗口设为零则立即禁用；新的副本上下限仍然有约束力。

只记录原始建议，不把稳定化后的输出反复写回历史，否则“因为之前保留了 5 个，所以继续记录 5 个”可能无限延长保护。历史最大值也不能主动扩容：一次失败的高建议或外部缩容，不应被历史反向改成扩容命令。

高频事件下，只按时间清理仍可能产生很多记录。实现用有界时间桶保存桶内最大建议和最新观察时间，使高值不会提前过期，代价是最多多保留一个桶宽。

相比把每条历史写进 status/ConfigMap，这种冷启动保护避免了历史与 Scale 两次写入之间的持久化协议和冲突合并，代价是重启后可能额外保留一个窗口。它叫“重建保护”，不叫“恢复了原历史”。[ADR 0002](adr/0002-cold-start-scale-down-protection.md)

## 6. 如何阅读验证证据

| 层次 | 能证明什么 |
|---|---|
| Provider 测试 | 给定 API 身份和 Prometheus 响应，归属、加权、拒绝和恢复行为符合规则 |
| Reconcile 测试与 envtest | 给定观测与时间，实际 Scale/status 交互、身份替换、冲突和保护行为正确 |
| 独立 Kind 验收 | 真实 API、Prometheus/cAdvisor、容器实例、负载及 leader 切换能走通完整链路 |
| 后续匹配压测 | 指定负载下是否改善请求成功率、延迟和副本占用 |

前三层不能替代最后一层。功能验收中看到扩容成功，不等于已经证明优于原生 HPA。运行当前集群验收的方法及具体结果见[验证记录](metrics-safety-validation.md)。

面试时可以顺着一次决策解释：如何确定指标属于谁、数据失效后如何处理、请求副本与观测副本为什么不同，以及重启后选择保守容量保留的原因。每一部分都有可观察的失败场景和明确代价。
